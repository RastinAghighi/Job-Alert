# job-monitor

Reliable monitoring platform for job sources. Watches the careers APIs of many
companies and alerts within minutes when a Canadian internship or co-op posting
appears.

**The canonical source of truth for this project is
[`JOB_MONITOR_MASTER_SPEC.md`](./JOB_MONITOR_MASTER_SPEC.md), vendored at the
repo root.** Read §39 before doing any work. Architecture is frozen for V1.

## Layout

Directories match spec §17 exactly. The dependency edges in each member's
`Cargo.toml` encode the §17 crate table, so an illegal edge is a compile-time
problem rather than a code-review problem.

```
crates/errors     -> (nothing)                              §9  taxonomy
crates/core       -> errors                                 PURE, SYNC, NO I/O
crates/ports      -> core, errors                           §17.1 traits only
crates/adapters   -> core, errors                           pure bytes -> RawJob
crates/engine     -> core, ports, adapters, errors          §11.3 orchestration
crates/infra      -> core, ports, adapters, engine, errors  concrete impls
bin/lambda        -> everything                             wiring only
bin/admin         -> core, ports, infra, errors             §19 source CRUD
```

`crates/core` and `crates/infra` are pre-populated with the exact module files
§17 enumerates, each an empty file carrying its one-line responsibility. Phase 1
and Phase 3+ fill them in. `crates/adapters`, `crates/engine` and `crates/ports`
have no submodules pre-created because §17 does not enumerate any for them.

## Verify locally

From a clean clone (PowerShell — no `&&` chaining):

```powershell
cargo generate-lockfile      # then commit Cargo.lock
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo doc --workspace --no-deps
```

Expect: clean build, zero warnings, **0 tests** (Phase 0 acceptance is "CI green
on an empty workspace"). CI runs the same four commands.

`Cargo.lock` is deliberately not committed yet — it must be generated by the
pinned 1.97.1 toolchain, not by whatever produced the skeleton. Once it is
committed, add `--locked` to the CI `test` step so a stale lockfile fails the
build.

## Deviations from §17, and why (per §39.6 — nothing changed silently)

**1. Library package names are prefixed `jobmon-`.** Directories are unchanged
(`crates/core`, `crates/errors`, …), but the Cargo *package* names are
`jobmon-core`, `jobmon-errors`, and so on.

A package literally named `core` shadows the sysroot `core` crate in the extern
prelude. Verified on 1.75: it does not produce a clean ambiguity error — the
local crate silently wins, and you get

```
error[E0432]: unresolved import `core::fmt`
error: cannot determine resolution for the derive macro `Debug`
       note: import resolution is stuck, try simplifying macro imports
```

anywhere in the workspace that touches `use core::…` or a derive. Since §17
specifies a *directory layout* and never pins a Cargo package name, renaming the
package is the smallest change that preserves §17's structure.

**2. The two binaries keep bare names: `lambda` and `admin`.** `admin` is
deliberately **not** `jobmon-admin`, because §19 documents the operator command
verbatim as `cargo run -p admin -- add-source …`. Neither name collides with a
sysroot crate.

## Flagged for later phases (not acted on in Phase 0)

**`bin/admin` will need a direct dependency on `jobmon-adapters`.** §17's table
allows admin to depend on `core`, `ports` and `infra` only — but §19 requires
`admin add-source` to validate "adapter exists, `endpoint_config` satisfies the
adapter's schema" and to perform "one live probe fetch + parse before
committing." That needs `adapters` directly; a transitive path through `infra`
is not enough in Rust. The edge is **not** added yet, so that Phase 6 makes it a
conscious decision rather than inheriting it. This is a gap in the §17 table, not
an invariant problem.

**Directory-name collision.** `crates/infra/` (the Rust crate) and the root
`infra/` (SAM template, §17 and Phase 6) are both called "infra". Both are
specified by §17. Root `infra/` is not created yet — Phase 0 explicitly forbids
any SAM template. Worth knowing before Phase 6 so the two are not conflated.

**`panic = "abort"` is deliberately absent** from `[profile.release]`. See the
comment in the root `Cargo.toml`: it would foreclose wrapping per-source
processing in `catch_unwind` (so one panicking source cannot abort a whole tick
and block the other claimed sources), and it breaks `#[should_panic]` under
`cargo test --release`. Decide it in Phase 6.

**Consider scoping `clippy::unwrap_used` / `expect_used` to non-test builds in
Phase 1.** Not imposed now because it is a judgement call that belongs with the
code it constrains, and Phase 1's ~70 tests will use `unwrap` freely.

## Owner checklist — the rest of Phase 0

These four items are in §32 Phase 0 but cannot be done from inside the repo.

- [ ] **Install `cargo-lambda`.** On Windows, Zig is required for
      cross-compiling to the Lambda Linux target, and `cargo install
      cargo-lambda` does **not** install it. Either use an installer that bundles
      Zig, or run `cargo lambda system --install-zig` afterwards. Verify with
      `cargo lambda --version` and `cargo lambda system`. The ARM64 target
      (§4 D4) is already pinned in `rust-toolchain.toml`, so no
      `rustup target add` is needed.
- [ ] **Confirm the AWS account is on the Paid Plan, not the six-month Free
      Plan.** §28.1 lists this as the footgun that takes the whole system with
      it: a Free Plan account auto-closes after six months or when credits run
      out. Billing console → Account settings → plan type. Always-free
      allowances (Lambda 1M invocations, DynamoDB 25 WCU/25 RCU, EventBridge
      Scheduler 14M) persist indefinitely only on the Paid Plan.
- [ ] **Create a $5 billing alarm.** AWS Budgets is the simpler path (first two
      budgets are free, region-agnostic). If you use a CloudWatch alarm on
      `AWS/Billing → EstimatedCharges` instead, note that the billing metric is
      **only published in `us-east-1`** — creating the alarm in `ca-central-1`
      produces an alarm that can never fire. Point it at an email address, not
      Telegram (§26: the money alarm and the primary channel should not share a
      failure domain either).
- [ ] **Push to GitHub and confirm CI is green.** That is the Phase 0 acceptance
      criterion: a clean clone builds and tests in CI.
